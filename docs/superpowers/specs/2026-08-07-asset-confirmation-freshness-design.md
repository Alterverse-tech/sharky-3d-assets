# 资产确认新鲜度与游戏意图隔离设计

## 目标

防止 Codex 把历史游戏留下的 `asset-sourcing-plan.json` 当成当前游戏已经获得用户授权，从而跳过完整资产确认板。

## 已确认原因

当前 Widget 在用户点击确认后生成持久化方案，其中包含 `confirmation.confirmed=true`、`confirmedBy="user"` 和 `confirmedAt`。本地校验器也只检查这些持久化字段。因此，这个文件可以证明历史选择曾被冻结，却不能证明当前资产任务刚刚获得授权。

本次错误发生在编排层：Agent 读取到旧方案后，把历史审计记录误当成当前确认事件。仅增加 `threadId`、`runId` 或方案哈希仍不能解决授权语义，因为这些字段同样会持久化、复制或过期。

## 方案比较

### 方案 A：只补 Skill 文案

规定新游戏必须展示确认板，旧方案只能预填。改动最小，但仍主要依赖 Agent 遵守规则。

### 方案 B：把历史方案绑定线程或时间

给文件增加 `threadId`、过期时间或任务 ID。它能减少部分误用，但持久化元数据仍不能证明当前用户动作，并会让合法的续作和跨线程恢复变复杂。

### 方案 C：游戏意图路由 + 当前任务实时确认门（采用）

先用游戏意图判断历史方案是否与当前游戏相关，再决定它能否用于预填。真正的执行授权只来自当前资产任务中的 Widget 确认事件；磁盘文件永远不能单独满足确认门。

## 核心边界

系统必须分开处理三个概念：

1. **历史选择快照**：`asset-sourcing-plan.json`，用于审计、复现和预填。
2. **游戏意图相关性**：判断历史快照是否描述当前游戏。
3. **当前执行授权**：当前资产任务中用户点击确认板后产生的实时事件。

历史快照不是授权凭证。意图相关性也不是授权；它只决定是否允许预填。

## 游戏意图判断

每次收到游戏生成、重做或资产接入请求时，先从当前请求和目标项目提取 `GameIntent`：

- 目标项目或游戏目录；
- 游戏摘要与核心玩法；
- 关键实体槽位的 `id`、`role` 和 `assetKind`；
- 每个实体需要的语义动作；
- 用户是否明确表达“继续、恢复、沿用刚才的游戏”。

将当前意图与历史方案的游戏摘要和槽位结构比较，得到四种结果：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| `active_same_task` | 当前资产任务已经存在实时确认，且新消息只是同一游戏的后续步骤 | 可继续执行已确认选择 |
| `related_history` | 历史方案描述同一游戏，但当前任务没有实时确认 | 用历史选择预填确认板，并要求重新确认 |
| `unrelated_history` | 游戏玩法、目标目录或关键实体明显不同 | 完全忽略历史选择，展示新的确认板 |
| `uncertain` | 信息不足或相似度冲突，无法可靠判断 | 按无关历史处理，不自动预填 |

意图判断必须保守。模型名称相同、同处一个仓库、或都包含“人物/飞机”等通用实体，不能单独判定为同一游戏。用户明确说“继续刚才的游戏”是强相关信号，但如果当前任务没有实时确认，仍只能预填，不能跳过确认板。

## 确认与执行流程

```text
收到资产相关游戏请求
→ 提取当前 GameIntent
→ 当前资产任务是否已有实时确认且意图一致？
  → 是：继续执行
  → 否：检查历史方案相关性
      → related_history：用历史选择预填
      → unrelated/uncertain：从默认推荐开始
→ 渲染完整资产确认板
→ 等待用户点击“确认资产方案并开始制作”
→ Widget 向当前对话发送确认结果
→ 才允许导入、生成或修改游戏代码
```

## 文件与工具语义

- 保留 `asset-sourcing-plan.json` 的确认时间和选择，作为历史审计信息。
- 给新方案加入稳定的 `intentSnapshot`，包含游戏摘要、目标项目标识和规范化槽位；旧文件没有该字段时一律视为 `uncertain`。
- `validate-asset-sourcing-plan.mjs` 只验证方案结构、选择关系和本地文件，不再把校验成功描述为“当前用户已授权”。
- Skill 明确禁止使用工作区读取到的 `confirmation` 字段满足当前确认门。
- 当前任务的实时确认应来自 Widget 发布到模型上下文的确认结果；如果上下文中没有这次确认，编排器必须停止在确认板。

后续可增加运行期授权票据，让导入工具拒绝没有当前票据的调用；该票据不写入项目。但首要修复仍是消除“持久化方案等于当前授权”的错误语义。

## 失败处理

- 找不到历史方案：正常展示新确认板。
- 历史方案缺少意图快照：按 `uncertain` 处理。
- 意图识别冲突：不猜测，忽略历史预填。
- Widget 确认失败：不导入、不生成、不修改游戏代码。
- 用户明确切换到另一个游戏：立即使当前任务的确认门失效，并重新进入资产确认阶段。

## 验收场景

1. 新游戏目录中存在另一个游戏的 `confirmed: true` 方案：必须展示新确认板。
2. 同一游戏历史方案存在，但在新任务中打开：可以预填，不能自动制作。
3. 同一资产任务确认后继续生成：不重复询问。
4. 用户确认跑酷游戏后改为飞机竞速游戏：旧确认立即失效。
5. 历史方案与当前游戏是否相关无法确定：必须按无关处理。
6. 本地校验器通过旧方案：只能报告结构有效，不能报告当前授权有效。

## 非目标

- 不用 Browser 或 Computer Use 判断任务相关性。
- 不因为同一任务中的普通后续消息重复打开确认板。
- 不用简单关键词匹配替代完整游戏意图判断。
- 不把线程 ID、时间戳或哈希单独当成用户授权。
